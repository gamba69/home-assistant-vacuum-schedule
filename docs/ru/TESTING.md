# Тестирование и проверка релиза

Каждый релиз проверяется на чистом дереве и повторно после распаковки финального архива.

## Обязательные проверки

```bash
pytest -q
python -m compileall -q custom_components tests
node --check custom_components/vacuum_schedule/frontend/panel.js
```

Дополнительно:

- разобрать каждый JSON-файл;
- убедиться, что `PATCH_*.md` отсутствуют;
- в `custom_components/` должен быть ровно один каталог интеграции — `vacuum_schedule`;
- `manifest.json` должен содержать `Vacuum Schedule`, `vacuum_schedule` и текущую версию;
- публичные actions должны использовать `vacuum_schedule.*`;
- старая строка `vacuum_scheduler` разрешена только в явном migration-коде/тестах/документации;
- проверить одинаковый набор файлов документации EN/RU/UK;
- проверить одинаковый набор translation keys EN/RU/UK для Home Assistant;
- исключить кэши и `*.pyc` из релизных архивов.

## Regression миграции 0.13.0

Тесты должны подтверждать перенос каждого собственного Store версии 0.12.61, обнаружение месячных Statistics Ledger chunks по старому индексу, создание новой записи с копией `data` и `options`, а также удаление старой config entry только после успешного копирования данных.

## Базовая точка

0.12.61: 974 теста успешно. В 0.13.0 эта база сохраняется и дополняется контрактами переименования, трёхъязычной документации и legacy-data migration.

## GitHub CI

Тот же проектный gate автоматически запускается при push в `main`, pull request, тегах версий и публикации релиза. HACS validation и hassfest остаются отдельными workflow. Генерируемые `*.patch` — локальные файлы доставки и никогда не должны попадать в Git.
